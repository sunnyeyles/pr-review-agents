01

Boot — the Action entrypoint

apps/action/src/index.ts

runEntrypoint() runs at import time, but returns immediately unless GITHUB_ACTIONS === "true" — so importing the module in a test does no work and needs no configuration.

runAction then resolves configuration in a deliberate order. Agent selection happens first, before a single client exists, because an unrecognised agent name is a typo in a workflow file and must cost nothing to discover.

Why it throws A review with no agents, or a silently dropped agents: secuirty, would report nothing — indistinguishable from a clean bill of health. So loadAgentDefinitions refuses a missing config instead of defaulting, and resolveAgentDefinitions rejects unknown names instead of ignoring them.
StepFunctionFails the run?
Load configured agentsloadAgentDefinitionsYes missing or malformed config
Narrow to the selectionresolveAgentDefinitionsYes unknown name
Model clientcreateModelClientYes unknown provider or missing key
Langfuse tracingcreateLangfuseRuntimeNo optional
Managed promptsloadManagedPromptsNo falls back per prompt
GitHub clientcreateTokenClientYes missing token

Tracing starts before the prompt fetch, so the fetch's own spans are captured; prompts resolve before anything that consumes them is built.

02

Is this even a review?

apps/action/src/event.ts · inspectEvent

Two outcomes, and the difference between them is the whole point of this file.

OutcomeWhenResult
Not a review Wrong event name, or an ignored action like labeled Logs review.skipped, step succeeds
Malformed Claims to be a supported pull_request event but fails the schema Throws — fails the workflow

Most workflow triggers are not reviews, so ignoring one quietly has to be a success. A payload that should have parsed and didn't is a bug worth failing over.

03

Load the pull request

packages/reviewer/src/review-pull-request.ts

Three GitHub reads, concurrently. This is the only place the review context is built.

One source of truth changedFiles is read by the agents and by validate. Because both read the same list, validation can never check findings against a different set of files than the one the agents actually reviewed.
04

The graph

packages/reviewer/src/review-graph.ts

Agent nodes are added dynamically — one per selected agent — each wired straight from START so they run concurrently. The three nodes after them run in sequence once every agent has settled.

4a · Each agent node

packages/ai/src/agents/runtime.ts · createReviewAgent packages/ai/src/agents/definition.ts · what an agent is

Every agent shares one runtime. A AgentDefinition — the three fields a config entry carries — supplies the role, the focus text, and the category. The loop, the six tools, the injection hardening, and the output contract are identical by construction, so a new agent costs a YAML entry and no code.

The cap bounds model calls, not tool round trips. A response with no tool uses always ends the run on the call it arrived on, so the cap can never burn a call the agent is unable to answer.

After parsing, the runtime filters findings down to the agent's own category. Cross-category leaks are dropped, never re-stamped — re-stamping would fabricate a claim the model never made, while dropping keeps category provenance deterministic.

The six tools

packages/ai/src/tools.ts

These are the only tools any agent ever gets. There is no write, comment, approve, merge, or execute tool anywhere in the package — so the restriction holds by construction rather than by prompt.

ToolReads
get_pull_requestTitle, description, author, branches, SHAs
list_changed_filesThe changed-file list
get_diffThe full unified diff
get_fileOne file at the head SHA — the proposed state
get_base_fileOne file at the base SHA — before this PR
search_repositoryCode search, always scoped to this repository

Every input is Zod-validated before it touches the GitHub client, and dispatchReviewTool never throws: failures come back as { ok: false } and reach the model as an error tool_result, so a bad tool call costs a turn rather than the run.

4b · join — the fan-in

LangGraph only runs this node once every incoming edge's source has completed. It re-sorts outcomes by the agent's input position, never completion order, so the result never depends on which agent happened to settle first.

One failed agent does not fail the review. All of them does.

4c · synthesise

packages/ai/src/agents/synthesiser.ts

One model call. No tools, no loop. It removes duplicates, merges overlapping findings, drops speculation, corrects severity where it is clearly wrong, and orders what survives most important first.

PathTriggersynthesis.outcome
SkippedZero candidates — nothing to refine, so no model call at all"skipped"
CompletedModel returned valid JSON"completed"
FailedBad output or an API error — the raw candidates are used instead"failed"

A synthesis failure never fails the review. It is safe to fall back to the raw candidates precisely because the synthesiser's output was never trusted either — both paths flow through the same chain next.

4d · validate — the trust boundary

packages/reviewer/src/validate-findings.ts

Seven deterministic steps, in this order. No I/O, no model, no mutation of its inputs.

  1. Schema validity — reviewFindingSchema (Zod)
  2. The category belongs to one of the run's agents — the schema cannot check this, since the set is known only at runtime
  3. The file exists among the PR's changed files
  4. The line is an added line in that file's diff, when a line is given
  5. Confidence ≥ 0.7 — CONFIDENCE_THRESHOLD
  6. Duplicate removal — the strongest of each group survives
  7. Cap at 10 — MAX_FINDINGS, keeping the strongest

"Strongest" is fully deterministic: severity rank, then confidence descending, then input order. Dedup runs before the cap, so duplicates — which several agents reviewing one diff produce routinely — cannot consume cap slots and leave the review short.

This is where bad output dies A fabricated file path, an invented line number, or a padded confidence score is dropped here — regardless of how confident the model sounded when it proposed it.
05

Render

packages/reviewer/src/render-check-run.ts

Pure — the caller owns the actual GitHub API call.

SituationConclusionWhy
No findings, no failuressuccess"No issues found"
Any findingsneutralAdvisory — the app never blocks or approves a merge
An agent failed, even with zero findingsneutralAn incomplete review must not publish a clean bill of health

Line-anchored findings also become inline annotations. Failed agents appear in the summary by name only — the error detail was already logged as agent.failed at failure time and is never re-emitted here.

06

Publish

apps/action/src/summary.ts · createFallbackPublisher

Try the check run first. On a 403 or 404, write the same rendered review to the workflow job summary and exit cleanly — that is the fork case, where GitHub hands the workflow a read-only token.

Everything else propagates and fails the step: 401 is a bad token, 429 is rate limiting, 5xx is an outage, and an error with no status at all is a network failure. None of those may masquerade as a delivered review.

The cost of being wrong is asymmetric in both directions, which is why the rule is this narrow. Too permissive, and a real GitHub outage renders as a clean review nobody investigates. Too strict, and every fork pull request fails CI.

Lifecycle log events

Every event of one review carries repository, pullRequestNumber, and headSha — so an operator can answer "what happened to the review for PR N?" from the logs alone.

review.started
  → review.loaded
    → agent.started ×N  → agent.completed / agent.failed ×N
    → synthesis.started → synthesis.completed / .failed / .skipped
    → findings.validated
  → review.published / review.published.degraded
